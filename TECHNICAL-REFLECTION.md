Review Ledger — Technical Reflection
Lars Klander | Track 5 | 5 November 2026
Planning and coordination
Review Ledger uses hierarchical decomposition, a validated dependency graph and evidence-driven replanning. The goal is to preserve intended behavior while addressing evidenced defects. Subgoals establish characterization tests, repair findings and demonstrate acceptance. An LLM proposes the plan; deterministic checks reject invalid dependencies, cycles and unsupported readiness. Failure can invalidate dependent actions while leaving unrelated evidence usable. This is more than a sequence of tool calls.
Google ADK runs parallel security, performance, style and test-gap reviewers. LangGraph owns the persistent lifecycle and human interrupts; ADK sessions remain subordinate review invocations. Git supplies revision isolation and Docker supplies execution isolation. Separating orchestration responsibilities adds serialization work but avoids competing approval state machines. Fixed specialists make coverage inspectable; a dynamic supervisor or free-form debate could explore unexpected concerns but would make cost and coverage less predictable. A single framework would be simpler, but the rubric requires two. A2A services and n8n routing would be justified by deployment or organizational needs, neither of which the prototype requires.
My contribution is the approval-bound evidence ledger: source, finding, assumption, plan revision, exact patch, human decision and validation outcome remain linked. I do not claim this pattern has no precedents. Four agents using the same model can share blind spots; agreement is not proof.
Human authority and observed failures
Permission binds to the exact executable change, its parent revision, plan and policy. A revised patch needs a fresh decision. Generating a proposal does not change a checkout; execution occurs in an isolated workspace after approval. Failed work is retained. Checkpoints do not make external side effects atomic, so ambiguous operations stop for inspection rather than silently repeating mutations.
Actual rehearsal failures exposed different weaknesses. Windows path lengths caused an AMBIGUOUS run; short workspace paths addressed the portability problem. A generated test then expected [1, 1, 1, 3] where the documented behavior required [1, 1, 3, 1]. Altering correct production code to satisfy that assertion would have introduced a regression. Approval establishes permission, not correctness.
Repeated approvals imposed real reviewer effort. Bounded literal-example checks and explicitly simulated preflights moved inexpensive checks earlier without granting permission. A rejected planner response also exposed missing raw-output retention; the precise defect could not be reconstructed. Raw responses are now saved before validation. Evaluation: separate questions, separate evidence
In the original frozen comparison, parallel specialists underperformed the single reviewer: held-out automatic macro precision was 0.411 versus 0.510, with recall 1.000 for both. Provider-reported token totals were 101,708 versus 34,945. Neither met the 0.80 precision target. Sparse labels may omit valid findings, but those original scores remain published. Fixture-oracle checks did not establish agent-generated repair success across that corpus.
A later Luna-authored holdout froze Gemini before twelve synthetic cases were created. Public inputs and private answers were separated, and outputs were locked before scoring. Original overall precision was 72.7%; after I accepted three additional test-coverage findings, adjudicated overall precision was 100%. Original/adjudicated macro precision was 85%/100%; recall was 100%/100% against eight/eleven known findings. The adjudicated targets are met on this set. This was post-score adjudication by the project author, not blinded external review; it does not prove that no other issues were missed. These are review findings, not eleven production bugs or a repair-success score.
Additional scope and verified repository repair
Beyond the original rubric path, I added a read-only dashboard, bounded Python repository intake, pinned public GitHub PR revisions and dependent repair steps. Assignment 5’s closed PR demonstrates historical intake, not a live PR repair. A broader development corpus exposed a role gap: no original specialist owned ordinary logic correctness. Adding a fifth reviewer improved complete outcomes from 2/8 to 8/8 across four related cases run twice: six repairs and two unchanged clean controls. Both deliberately injected failure cases recovered. The comparison is tuned development evidence; the failures were harness injections and benchmark approvals were simulated.

Limits and next steps
Passing tests supports sampled behavior, not whole-program equivalence or general reliability. Support remains bounded Python with stdlib tests, selected context and no dependency installation. Private Git hosts, arbitrary repository setup and a personally approved live PR repair remain undemonstrated. The next evaluation should use independently reviewed labels, broader unseen repair cases, repeated runs and a non-replanning baseline. The primary recording follows the established rubric path; additional work is identified separately. Rehearsal duration and the final recording remain to be measured.
